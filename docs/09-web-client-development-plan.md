# Web 客户端开发计划 V2

> **历史设计文档。** 本文记录常规 Web 原型路线，不对应当前可运行产品。当前仅交付
> 《冠军联赛99日》，实现与验收以赛事文档和训练系统 V3 为准。

## 决策状态

**已确认**

- 当前产品只提供 Web 版本，全部开发资源优先用于浏览器可玩闭环。
- 移动端、APK 和应用商店不进入当前路线图，也不作为代码抽象与验收约束。
- 首版继续以单机主线和本地存档为边界；加入浏览器本机账号，用于区分昵称和多份进度，
  但不把它视为云账号或在线服务。

**当前技术方向**

- Web 客户端采用 React、TypeScript 和 Vite，初赛阶段只以大屏 Chrome 为产品与验收
  环境。设计基准为 `1440×900` 及以上，最低运行画布为 `1280×720`；不为小屏压缩
  字号、卡面、系统面板或交互层级。
- Python 保留为角色物化、批量模拟和数值校准工具；浏览器运行时不执行 Python。
- 客户端比赛运行时最终使用 TypeScript，并通过固定 Seed 的 JSON 用例与 Python
  参考实现核对规则一致性。

## 为什么专注 Web

当前仓库已经具备版本化角色数据、88 人运行 Box、阵容校验、文字比赛和批量校准，
Web 首版用最短链路验证以下核心问题：

1. 不熟悉足球的玩家能否在角色陪伴下理解前中后、具体位置和标准阵型。
2. 玩家能否理解 Box、阵容、阵营羁绊和赛前指令之间的关系。
3. 文字比赛与赛后报告能否清楚表现位置、阵型、技能及其对比赛结果的影响。
4. 卡面、角色详情、俱乐部剧情和球星卡收藏能否建立角色与足球记忆。
5. 单机进度、比赛 Seed 和数据版本能否稳定保存与复现。

Web 可以保留快速开发、部署和调试效率，也最适合当前以文字比赛、卡牌收藏和管理
界面为核心的产品形态。

## 总体架构

```text
策划源 / SQLite 快照
        ↓
Python 物化与校准工具
        ↓
版本化玩家公开 JSON ─────────────┐
                                  ↓
                         React + TypeScript Web
                         ├── 经理办公室
                         ├── 球员更衣室 / 阵容
                         ├── 赛程 / 比赛 / 赛后报告
                         ├── 球星卡商店 / 招募
                         └── 本机账号 / 分账号存档
                                  ↓
                         Vite 静态 Web 构建产物
```

### 规则与运行时边界

- Python 是数值研究和参考实现，不作为 Web 运行时依赖。
- 角色、关卡和比赛输入必须使用玩家公开数据，不能把真实原型姓名、来源 URL 或
  内部评分字段打入客户端。
- 每场比赛保留 `seed`、`rules_version`、`character_data_version` 和完整阵容输入。
- Python 与 TypeScript 使用同一批固定 Seed JSON 用例；同版本规则必须产生一致的
  关键事件、比分和技能贡献结果。
- 比赛事件由模拟器生成，UI 只负责展示，不在结果返回后临时拼接影响比赛含义的事件。

### 浏览器适配边界

浏览器能力通过小型接口集中管理，避免页面直接散落本地存储和资源路径逻辑：

```text
LocalAccountStore 注册、登录、昵称和当前本机会话
GameStorage       按 UID 读取、保存和迁移浏览器单机进度
AssetResolver     解析资源 Manifest 与 Web 发布地址
```

这两个边界服务当前 Web 的可测试性和版本迁移，不为尚未排期的平台预留额外接口。

## 开发里程碑

### W0：小规模比赛协议

**已实现，不依赖御三家主线定稿**

- 将现有比赛入口参数化为 `three_player_training`、`five_a_side` 和
  `eleven_a_side` 三种模式。
- 3 人训练不要求正式门将，不启用正式阵型、身价额度和阵营羁绊。
- 5v5 使用一名门将和四名外场球员，继续复用能力、技能、Seed、事件和报告模型。
- 11v11 保持当前 V4 行为与校准基线不变。
- 暂不实现仍待主线确认的 9v9。
- 定义稳定的比赛输入、输出和固定 Seed JSON 用例，为 TypeScript 移植提供契约。

验收标准：现有 11v11 测试不回退；3 人和 5v5 均可复现，并输出与 11v11 同构的
事件、技能贡献和赛后报告。

当前实现为 `text-match-modes-v1`，固定 Seed 契约位于
`data/contracts/text-match-seed-contract-v1.json`。本阶段只完成 Python 参考实现；
TypeScript 客户端运行时仍属于后续 Web 里程碑。

### W1：Web 工程基础

**已实现**

- 已在 `web/` 建立 React、TypeScript 和 Vite 工程。
- 构建准备步骤只复制 `expanded-roster-v1.public.json`、比赛 Seed 契约和资源 Manifest
  进入 Web 工程，开发服务器不会暴露仓库内的内部数据目录。
- 已建立游戏化经理办公室和固定底部五入口：经理办公室、球员更衣室、训练中心、赛程、
  球星卡商店。
- Web 外壳固定为一个视口高的游戏舞台，页面本身不滚动；经理办公室背景覆盖画面，
  登录宣传图完整显示。左上用户入口、固定纱夜台词、序章按钮和底部入口作为独立 HUD
  图层，不使用横跨画面的顶部栏。
- 首页暂不展示目标、俱乐部状态、球员资料和下一场快捷按钮，待剧情内容确定后再接入。
- 当前版本已开放经理办公室、球员更衣室、训练中心、赛程与球星卡商店五个入口。
- 经理办公室已接入背景、氛围、人物和 UI 四层场景框架；御三家和八名六星仍绑定桌面
  人物锚点，并为底部主导航保留安全区；当前初赛运行时固定纱夜，不开放看板娘轮换。
- `LocalAccountStore` 使用 Web Crypto 保存加盐密码摘要；`GameStorage` 使用带 Schema
  版本、按 UID 隔离的浏览器 `localStorage`；这只是本机多账号，不提供云账号能力。
- `AssetResolver` 只解析
  Manifest 中的 `public_path`，不会把本地母版路径当成浏览器地址。
- 已提供开发、测试、类型检查和生产构建命令；构建后检查内部原型字段与源媒体泄漏。

验收标准：可以从全新 checkout 启动开发服务器并生成静态生产构建；在 Chrome
`1440×900` 及以上视口中完成核心流程，`1280×720` 保持可操作；生产构建不包含内部
角色原型字段与高分辨率母版。移动端与小屏不进入初赛验收。

### W2：当前系统试玩纵切

**主体已实现，正式主线接入待完成**

- 开放球员更衣室，接入真实卡面、角色详情和三人阵容选择；技能名称、触发条件和
  效果说明只在这里的角色详情中展示，不进入卡面。
- 开放赛程，接入赛前指令、文字比赛过程和赛后结算的最短闭环。
- 主线未定稿时使用明确标记的开发关卡和固定测试阵容，不提前编写御三家剧情。
- 御三家身份、关系与技能定稿后，再把纵切入口替换为正式开局流程。
- 球星卡商店已接入阵营十连、概率与保底、下滑撕包、逐张翻牌和收藏持久化；不使用
  普通自由球员市场替代招募系统。
- 先验证一场比赛的完整体验，不在本阶段扩展经济、赛季或活动系统。

验收标准：玩家能够在浏览器内完成一次阵容选择和可复现比赛，查看技能影响与角色
贡献；刷新页面后可以恢复已保存进度并重新打开该场比赛记录。

当前进度：球员更衣室的真实卡面、已持有列表、等级、位置、能力和独立球员档案已实现；
赛程已实现分层的战术与阵容页、11 人选人、一键推荐、全自动文字对局、技能
切入与赛后报告；球星卡商店已实现八阵营封装、首次十连保证、六星软保底和重复卡收藏。
卡包目录与单包购买详情已分层；训练中心首页、基础训练室、技能库和单技能详情已分层。
训练系统已实现两个实时训练槽、基础能力成长、每日开发补给和确定性技能研习；更衣室
已实现重复卡升星与分星级技能槽，配置技能会进入文字比赛能力和事件计算。正式三人
训练关卡与比赛记录存档仍属于后续纵切范围。

### W3：Web 首版核心循环

- 接入正式御三家开局，用角色对话、站位选择和赛后发现完成前中后教学。
- 接入五人社区赛和渐进阵容流程，再把当前 11 人战术页作为标准位置与阵型的正式解锁。
- 为一键推荐增加位置与阵型理由，为比赛结算增加与玩家选择相关的“本场足球发现”。
- 在已完成的卡包抽取、Box 扩张和基础养成原型上，加入主线关卡、奖励结算与比赛记录。
- 先以首战纪念卡介绍球星卡，再开放常规阵营卡包和收藏档案。
- 用老俱乐部、球迷组织、工作人员、参赛资格和首个赛季串起现有功能入口。
- 校准大屏布局、卡面展示尺寸、连续页面切换和长文本报告体验。
- 建立静态 Web 发布与版本回滚流程。

本阶段仍不实现异步天梯、真实支付、推送、服务端账号体系或云存档。

## 资源策略

`assets/cards` 中的高分辨率 PNG 是美术源和验收资产，不应全部作为 Web 首屏资源。
统一资源契约已经由 `asset-manifest-v1` 和 `runtime-assets-v1` 实现，完整规则见
[资源 Manifest 与本地资产管理 V1](10-asset-management.md)。客户端阶段继续完成发布
variant 和 TypeScript `AssetResolver`：

- 为 Box 列表生成小尺寸缩略图，为详情页生成压缩展示图。
- 保留原始 PNG，不让客户端运行时直接扫描或加载整个源资产目录。
- Web 按页面和角色懒加载；首屏只下载当前流程需要的资源。
- 统一通过逻辑 `asset_id` 和 Manifest 解析资源路径，避免 UI 硬编码文件名。
- 记录发布资源版本，使比赛记录、角色数据和卡面可以独立升级与回滚。

## 初版明确不做

- 非 Web 客户端、安装包和应用商店发布。
- 安装型 PWA、推送通知和后台任务。
- 服务端账号、跨设备云存档和在线多人服务；本机账号只用于当前浏览器的身份与存档隔离。
- Google Play 支付、真实货币商品或商业化 SDK。

这些能力只有在 Web 首版验证核心循环后，经过新的产品决策才可能进入路线图。
